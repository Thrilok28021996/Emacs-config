#+TITLE: Org tutorial — this configuration, end to end
#+AUTHOR: Thrilok
#+STARTUP: overview

A guided course for the configuration as it exists now, from "what am I looking
at" to "how do I extend it". Every key, path and behaviour in here was checked
against the running system; the key table in =cheatsheet.org= is generated from
the live keymaps.

- Reference: =cheatsheet.org=
- Architecture and reasoning: =ORG-PKM.org= (=C-c k H=)
- What is proven: =VERIFICATION.org=
- Gates: =./emacs-sync.sh verify=

Run Emacs in a terminal (=emacs -nw=) and keep this file open. Every lesson
ends with something to do and something to check.

* Lesson 0 — Orientation (10 min)

Emacs here has two halves that do not interfere:

1. *A coding editor*, built-in only, tuned to start fast (~0.15 s).
2. *A knowledge system* in plain Org files — the zettelkasten under
   =~/knowledge/= and the projects tree under =~/projects=/, loaded from
   =lisp/= by a single block at the end of =init.el=.

The knowledge system is the point of this tutorial.

*Why plain text:* every note is a =.org= file you can grep, diff, sync and
version with git. No database owns your knowledge. The one database in the
system (=org-roam.db=) is an index that is rebuilt from the files whenever you
want, and =VERIFICATION.org= proves that rebuilding it changes no file.

*Where things live:*

| Path | What |
|---|---|
| =~/knowledge/literature-box/= | notes taken from sources: =001.org=, =002.org=, … |
| =~/knowledge/main-box/= | permanent notes: =1.org=, =1-1.org=, =1-1a.org=, … |
| =~/knowledge/main-box/index.org= | the hand-curated map of the main box |
| =~/projects/inbox.org= | unsorted capture |
| =~/projects/projects/= | one file per project |
| =~/projects/learning/= | one file per learning subject |
| =~/projects/references/= | one file per source, plus the reading queue |
| =~/projects/daily/journal.org= | journal, weekly date tree |
| =~/projects/dashboards/= | generated views |
| =~/projects/attachments/= | attached books and files |
| =~/projects/templates/= | skeletons used when creating files |

Zettel files are created and numbered by hand — no command assigns a number.

*Do this now:* open Emacs, press =C-c ?=. That buffer lists every =C-c= binding
this configuration defines, generated live. Scroll it once — you never have to
memorise a key from a document again.

*Check yourself:* =C-c k H= opens =ORG-PKM.org=. If both work, the knowledge
layer loaded.

* Lesson 1 — Org fundamentals you will actually use (20 min)

A heading starts with stars. More stars, deeper level. =TAB= folds the subtree
under point, =S-TAB= cycles the whole buffer. That is the entire navigation
model, and it is enough for files of thousands of lines.

Link a heading to another: =C-c C-l=. With =org-return-follows-link= on, RET on
a link opens it. =C-c C-o= opens the link at point without moving point first.

Move structure, not text: =M-<up>= / =M-<down>= move the subtree under point, or
a selected region. =M-left= / =M-right= promote and demote. Renaming and
reordering by hand is how outlines rot.

For source code inside a note, use a block:

#+begin_src org
  #+begin_src python
  print("runs with C-c C-c")
  #+end_src
#+end_src

=C-c C-c= inside the block runs it and shows the result beneath.

*Do this now:* in =inbox.org= under =* Ideas=, write three headings with
different star counts, fold each with =TAB=, then move the middle one up with
=M-<up>=.

* Lesson 2 — The eight-state workflow (25 min)

A heading becomes a task when it starts with a keyword. This configuration has
one sequence, shared by every file:

#+begin_example
BACKLOG(b) TODO(t) NEXT(n) DOING(o) WAITING(w) REVIEW(r) | DONE(d) CANCELLED(c)
#+end_example

=C-c C-t= then the letter jumps straight to that state. =S-right= / =S-left= on
the keyword cycles without the menu.

| State | Means | Why it exists |
|---|---|---|
| BACKLOG | captured, not committed to | keeps ideas without letting them nag |
| TODO | committed, unscheduled | the honest default for real work |
| NEXT | the next physical action | a project with no NEXT is stalled, and the dashboard says so |
| DOING | in progress now | one place to look when you resume |
| WAITING | blocked on someone else | blocks its subtasks, because you cannot act on it |
| REVIEW | finished, needs a second look | catches sloppy completion |
| DONE | terminal | writes a =CLOSED:= timestamp into a =LOGBOOK= drawer |
| CANCELLED | terminal, abandoned | disappears from every board |

Two behaviours worth knowing, because they surprise people:

- *WAITING blocks children.* =org-enforce-todo-dependencies= is on, and WAITING
  counts as open. A waiting parent cannot be completed while subtasks are open —
  and its children are blocked too. That is deliberate: a parent you cannot act
  on is not work you can do.
- *Every file mirrors the sequence with its own =#+TODO:= line.* The kanban
  boards derive their columns from the TODO keywords of the files they scan, so
  a file with a different set would silently change a board's shape.

Recurring tasks use plain repeaters on the timestamp: =+1w= shifts from the
current date, =++1w= from the last completion, =.+1d= from today. No habit
graphs — they are agenda noise in a terminal.

Dependencies beyond parent/child use the =ORDERED= property. =org-depend= is not
used: it lived in Org's contrib directory, which Emacs 31 no longer ships.

*Do this now:* in =inbox.org=, create =** NEXT try the eight states=, then cycle
it through DOING and REVIEW with =C-c C-t=. Mark it DONE and look for the
=:LOGBOOK:= drawer under it.

*Check yourself:* the drawer contains =CLOSED: [timestamp]=. That line is what
"completion history" means here — no separate log file.

* Lesson 3 — Capture, before the thought escapes (20 min)

Capture exists so you never navigate to a file in the middle of something else.

| Key | Template |
|---|---|
| =C-c k i= | inbox item — fastest path, one keystroke |
| =C-c k t= then =i= | inbox item |
| =C-c k t= then =t= | task in a project — prompts for which project |
| =C-c k t= then =l= | task in a learning subject |
| =C-c k t= then =j= | journal entry, weekly date tree |
| =C-c k t= then =n= | someday idea |
| =C-c k t= then =r= | source / reading entry |

=t= and =l= prompt with the actual file names, so you never type a path. Finish
a capture with =C-c C-c=; abort with =C-c C-k=.

*Refiling* is the other half. =C-c C-w= moves the subtree at point to another
heading, choosing by outline path. Targets are the agenda files up to level 3.
Refiling is how the inbox gets emptied.

*Do this now:* =C-c k i=, type "test capture", =C-c C-c=. Then open
=inbox.org=, put point on it and refile it somewhere with =C-c C-w=.

*Check yourself:* after =C-c k t= → =t=, the prompt lists your real project
files. If it says "No files yet", you have no projects — Lesson 5 fixes that.

* Lesson 4 — Agenda and the three dashboards (25 min)

The agenda is a *view*: editing an item there edits the real heading in its real
file.

| Key | What it opens |
|---|---|
| =C-c o a= | the agenda dispatcher |
| =C-c k a= | dispatcher, after reloading the knowledge file list |
| =C-c k D= | home: today's schedule, next actions, in progress, waiting, review |
| =C-c k P= | projects: open project tasks grouped by state |
| =C-c k L= | learning: open learning tasks, revision |

Inside =*Org Agenda*=: =t= set state, =s= schedule, =d= deadline, =r= refile,
=f= / =b= next/previous span, =g= refresh, =q= quit.
=org-agenda-window-setup= is =current-window=, so =q= returns you exactly where
you were, not to a second pane.

*Why three dashboards and not one:* the project view is restricted to
=projects/=, the learning view to =learning=. A learning task never
appears on the project page. Both are grouped by state with org-super-agenda, so
"Doing" and "Next" are buckets rather than a chronological list.

*Which files the agenda reads:* =~/projects/inbox.org= plus every =.org=
file directly inside =~/projects/projects= and =~/projects/learning=. It
points at the *directories*, so a new project file is picked up with no
configuration change. Dashboards and zettels are excluded on purpose — they
are views and knowledge, not sources of actions.

*The same information as files:* =~/projects/dashboards/= contains generated
blocks (org-ql queries over your files) that you can read and grep without
opening the agenda. =C-c k b= regenerates all of them. An empty section says
"Nothing here" rather than showing a stale line.

*Do this now:* =C-c k D=. Find one item, press =t= on it to change its state,
then =g= to refresh and watch it move.

*Check yourself:* the same change is visible in the item's own file. Nothing was
copied.

* Lesson 5 — Projects, learning subjects and kanban (30 min)

*Creating.* =C-c k p= asks for a name and writes
=~/projects/projects/<slug>.org=: an ID drawer at the top, the workflow
line, Goal / Milestones / Tasks / Backlog / Board / Notes sections. =C-c k l=
does the same in =learning/= with a subject-shaped skeleton. Neither will
overwrite an existing file — a typo in a name is refused, not destructive.

*Thinking in two shapes.* A project file describes what you are building. A
learning file describes what you are studying. Reusable concepts do not belong
in either: they go in the zettelkasten (=~/knowledge/main-box/=) and get linked
from both. That one rule is what stops the system from turning into three
copies of the same paragraph.

*Boards.* Every project and subject file ends with a =* Board= section holding a
dynamic block. Put point on the block and press =C-c C-c= to render it; =C-c k b=
renders everything at once.

| Key | Moves the task |
|---|---|
| =C-c k m= then =a= / =h= | back one state |
| =C-c k m= then =d= / =l= | forward one state |
| =C-c k m= then =w= / =k=, =s= / =j= | reorder rows |

The row is a *link*, not a copy. Moving it runs =org-todo= on the heading in the
task's own file, then saves that file. The consolidated board in
=dashboards/projects.org= works the same way across all projects and subjects at
once.

*Honest limitation:* each cell holds a full Org link, so a seven-column board
renders at roughly 300 characters per line and does not fit a terminal. The fix
is one line on the block:

#+begin_src org
  #+BEGIN: kanban :range (TODO . REVIEW) :skip-columns ("CANCELLED")
  #+end_src

BACKLOG and DONE stay real states; they stop being columns. =:compressed t=
trades width for height.

*Do this now:* =C-c k p= → "first project". In its Tasks section add
=** TODO wire the first thing= and =** NEXT read the second thing=. Render the
board with =C-c C-c= on the block. Open =C-c k B=, put point on the TODO row,
press =C-c k m= then =d=. Open the project file: the heading is now NEXT.

*Check yourself:* the other task did not move. If it did, you have found the
bug the stage-2 checks exist for.

* Lesson 6 — Permanent notes and backlinks (30 min)

Org-roam turns each document into a *node* you can link to.

*What becomes a node:* any file created from a template — it starts with a
property drawer holding an ID, above the first heading:

#+begin_src org
  :PROPERTIES:
  :ID:       6f1c…
  :END:
  #+TITLE: Vector databases
#+end_src

Headings are *not* given IDs automatically. A node nothing links to is pure
maintenance cost, so you opt in per heading with =M-x org-id-get-create= when
something worth linking lives inside a file.

*Making and linking notes*

There is no template for a zettel, on purpose: a template cannot know the next
number. You make one by hand and give it identity with one key:

| Key | Does |
|---|---|
| =C-c k e= | give the file at point the ID drawer the index needs |
| =C-c k f= | find a zettel by title |
| =C-c o i= | insert a link to a zettel at point |
| =C-c k v= | backlinks panel for this note |
| =C-c k s= | re-index; reports node and link counts |
| =C-c k g= | the graph, in your browser |

*Do this now:* =C-x C-f= =~/knowledge/main-box/1-1.org=, write =#+TITLE: The
next note=, then press =C-c k e=. The numbering is yours: =1-1= continues the
topic of =1=, =1-1a= branches within =1-1=, =2= starts a new topic.

*The index is disposable.* =~/.emacs.d/org-roam.db= is built from the Org files.
Delete it, run =C-c k s=, and you get the same nodes and links back — the
stage-3 checks delete it, rebuild, and compare every zettel byte for byte. The
projects tree is outside the index entirely.

*Do this now:* in a project file, press =C-c o i= and insert a link to the
zettel you just made. Open the zettel and press =C-c k v=.

*Check yourself:* the backlinks panel lists the file you linked from. If it
does not, run =C-c k s= and look at the reported counts.

* Lesson 7 — Reading: sources, books and status (20 min)

Two files do two jobs:

| File | Job |
|---|---|
| =references/<slug>.org= | one source: summary, critique, quotes, the attached file |
| =references/tracking.org= | the queue: what is unread, what is in flight |

| Key | Does |
|---|---|
| =C-c k r= | new source note |
| =C-c k A= | attach a file (copied into =attachments/<id>/=, never beside the note) |
| =C-c k o= | open the first attachment |
| =C-c k S= | set STATUS: unread, reading, done, abandoned |
| =C-c k R= | open the queue |

An =.epub= opens in =nov-mode= and is rendered *as text*, which is why reading
works in a terminal at all. =n= / =p= move between documents, =TAB= follows links
inside the book.

=STATUS= records =STATUS_CHANGED=, and =done= also records =FINISHED=. The home
dashboard's reading block is an org-ql query over the reference directory.

*Two things this deliberately does not do:*

- *PDF.* A terminal displays no pages, and without pdf-tools there is no text
  layer either. Read PDFs outside Emacs; keep the notes here.
- *Annotations on the text.* =nov.el= has no annotation feature — no highlight
  store, nothing to sync. Notes about a book are Org notes, linked to the source
  note. Nothing pretends otherwise.

*Do this now:* =C-c k r= → "test book", =C-c k A= → pick any =.epub=, =C-c k S= →
reading. Then =C-c k d= and find it in the reading block.

*Check yourself:* the attachment is under =~/projects/attachments/= and the
source note contains a link to it. =git -C ~/projects status= shows the book as
new.

* Lesson 8 — Time: clocking (10 min)

| Key | Does |
|---|---|
| =C-c o I= | clock in on the heading at point |
| =C-c o O= | clock out |
| =C-c o R= | insert a clock report table at point |

Clocks persist across restarts, and the mode line shows today's total. Task
durations land in the same =LOGBOOK= drawer as completion timestamps, so time
and history live with the task rather than in a separate file.

*Do this now:* clock in on a task, wait a minute, clock out, then =C-c o R=.

* Lesson 9 — Tables and code in notes (15 min)

Org tables are text, and Emacs will maintain their alignment and formulas.

| Key | Does |
|---|---|
| =TAB= | next cell; at the end of a row, creates a new row |
| =M-left= / =M-right= | move the column |
| =C-c -= | insert or delete a horizontal separator line |
| =C-c *= | recalculate the table |
| =C-c C-c= | realign, or evaluate a formula |

One catch worth knowing: =C-c C-c= on a line inside a *dynamic block* updates the
block instead of just realigning. That is how boards and dashboards refresh.

Code blocks run with =C-c C-c= and support =:results= headers. Python, shell and
Emacs Lisp are enabled. =org-confirm-babel-evaluate= is nil, meaning code runs
without asking — do not paste blocks you have not read.

*Do this now:* write a two-column table, add a row with =TAB=, then a formula
with =C-c C-c= in a =#+TBLFM:= line.

* Lesson 10 — The coding half (20 min)

Built-in only, and untouched by everything above.

| Key | Does |
|---|---|
| =C-c c c= | compile |
| =C-c c p= | run the current Python file |
| =C-c c r=, =C-c c a=, =C-c c f= | eglot rename / code actions / format |
| =C-c c d= | find references |
| =C-c e n=, =C-c e p=, =C-c e b= | next / previous / list diagnostics |
| =C-c p f=, =C-c p p= | find file in project / switch project |
| =C-c g g=, =C-c g c=, =C-c g p= | magit status / commit / push |
| =C-c v a=, =C-c v d= | activate / deactivate a conda env |
| =C-c t t= | toggle theme |

=eglot= starts automatically in Python and C/C++ buffers; =flymake= runs in every
=prog-mode= buffer. *treesit* grammars are used for Python, C, C++, JS, JSON,
CSS, TypeScript and Bash when installed, with the classic modes as fallback.

Completion is built in: =fido-vertical-mode= in the minibuffer,
=completion-preview-mode= while typing code (not in prose, where it is noise),
=imenu= for jumping to definitions. There is no third-party completion stack:
that is the deliberate trade for a 0.15 s start.

*Do this now:* open a Python file, break the syntax, and fix it using
=C-c e n= to jump to the diagnostic.

* Lesson 11 — How this is put together, and how to trust it (20 min)

*The loading order:* =init.el= does the coding configuration, then a single
block at the end loads five modules from =lisp/=:

| Module | Responsibility |
|---|---|
| =my-org-pkm.el= | directories, workflow, discovery, capture, creation, block refresh |
| =my-kanban.el= | board parameters, refresh, and a corrected row resolver |
| =my-roam.el= | Org-roam over the zettelkasten, IDs, backlinks, keys |
| =my-dashboards.el= | generated blocks (org-ql) and the three agenda views |
| =my-reading.el= | EPUB, attachments, reading status |
| =my-help.el= | the generated key table and documentation access |

Nothing in =lisp/= is loaded before =init.el= finishes, so the coding path's
startup is unchanged. Heavy packages (org-ql, org-super-agenda, nov) load on
first use, not at startup.

*Gates.* Everything claimed in these documents is checked:

#+begin_src sh
  cd ~/.emacs.d
  ./emacs-sync.sh verify     # CONFIG_OK + all checks + load time
  ./emacs-sync.sh test       # just the checks
  ./emacs-sync.sh benchmark  # just the load time
#+end_src

The checks create their own fixtures and delete them again. They cover file
creation, agenda discovery, board rendering, moving a task and confirming the
right one moved, backlinks, deleting and rebuilding the index, dashboard
numbers, a real EPUB, the backup archive round-trip, and performance at 40
projects. =VERIFICATION.org= maps every acceptance criterion to the check that
proves it.

*Backups.* =~/projects/bin/backup.sh= commits pending work in both
repositories and archives each, including =git=. The archive is the fallback
for what git cannot fix.

*Do this now:* =./emacs-sync.sh verify=. Read the last line.

*Check yourself:* "0 failures". Then =git -C ~/knowledge status --short= and
=git -C ~/projects status --short= print nothing — the tests clean up after
themselves.
