This tutorial teaches Org against the *previous* configuration. Lessons 0–2 are
mostly still true; Lessons 3 and 4 taught a workflow and a dashboard that no
longer exist, so they have been rewritten. Anything else that mentions
=~/Documents/garden/=, consult, org-modern, olivetti or a two-sequence TODO
setup is stale: Org now lives in =~/knowledge/=, the config is built-in only,

|=C-c ?=| lists every key this configuration actually defines. =ORG-PKM.org=
(=C-c k H=) is the architecture document, and =~/knowledge/README.org= describes
the data.

This is a *hands-on* learning path for the Org setup in your =init.el=. Every
lesson uses your real keybindings and your real files (=~/knowledge/=).
Do the "▶ Do this now" steps in order — the point is muscle memory, not reading.

Pair this with =cheatsheet.org= (=C-x C-f ~/.emacs.d/cheatsheet.org=): tutorial
teaches the flow and the *why*, cheatsheet is the lookup card once you know
what you want. Where cheatsheet gives you the numbered steps, this file gives
you the reasoning and the practice.

Suggested pace: one lesson a day for ~3 weeks. By the end the keys are reflex
and you understand *why* each piece of config is set the way it is — so when
something behaves oddly, you know which knob in =init.el= to check.

* Lesson 0 — Orientation (10 min)
*What Org is:* plain-text =.org= files that fold into outlines. Headings start
with =*=. Everything else (agenda, roam, capture, kanban, SRS) is layered on
top of that one idea — a heading with a keyword and some properties. Nothing
in this setup is magic; it's all outlines plus metadata plus Elisp that reads
the metadata.

*Why plain text:* every file here is =grep=-able, diff-able, sync-able with
git, and outlives any specific tool. If Org disappeared tomorrow the files
would still be readable. That's the whole design philosophy behind Org, and
why this config leans on plain files instead of a database-backed app — except
for org-roam, which *does* keep a SQLite cache (see Lesson 7) purely as a fast
index over the same plain files, never as the source of truth.

*Your file layout* (all under =~/knowledge/=, set by =org-directory=):
| File                  | What lives here                       |
|-----------------------+----------------------------------------|
| inbox.org             | quick capture dump — sort later       |
| journal.org           | daily log (datetree)                  |
| reading.org           | books + reading notes                 |
| reviews.org           | spaced-repetition items               |
| work/tasks.org        | work next actions                     |
| work/projects.org     | work project index                    |
| work/projects/*.org   | individual work project files (auto-added to agenda) |
| personal/tasks.org    | personal next actions                 |
| personal/projects.org | personal project index                |
| personal/projects/*.org | individual personal project files (auto-added) |
| people/*.org          | org-roam person nodes (Lesson 8)       |
| (any) *_archive       | archived/done items, out of agenda    |

*How agenda-files is actually built:* it isn't a static list. =init.el= starts
with the eight named files above, then globs =work/projects/*.org= and
=personal/projects/*.org= and appends whatever it finds. Practical effect: drop
a new file in =work/projects/= and it's in your agenda on the next Emacs
restart — no config edit needed. Restart is required because the glob runs
once at startup, not on a timer.

▶ Do this now: =C-c o r= (roam find) — type any word, hit RET on "create". You
just made your first node. =C-x C-f ~/knowledge/= to see your files.
Then =C-x C-f ~/knowledge/notes/projects/= and note it's empty until you create
a project with =C-c k p=.
(or not) — that's the directory the glob watches.

* Lesson 1 — Structure: headings, folding, lists, links (20 min)
The whole editor is an outline. Master folding and movement first — everything
else in this tutorial assumes you're fluent with these.

| Key          | Action                      |
|--------------+------------------------------|
| M-RET        | new heading at same level   |
| TAB          | fold / unfold this heading  |
| S-TAB        | fold / unfold whole file    |
| M-LEFT/RIGHT | promote / demote heading    |
| M-UP/DOWN    | move subtree up / down      |
| C-c C-n/p    | next / previous heading (same level) |
| C-u C-u TAB  | show only top-level headings (overview) |

*Startup folding:* this file itself has =#+STARTUP: overview= at the top,
which is why it opens fully folded — that's an Org file setting, not a global
one. Your own notes default to fully open unless you add that line.

Lists: start a line with =-= or =1.=. =M-RET= makes the next item. =C-c C-c= on
a =[ ]= checkbox toggles it. A checkbox list under a heading shows progress —
add =[/]= or =[%]= after the heading text and it auto-updates as a counter
(e.g. =* Groceries [2/5]=).

Links: =C-c C-l= insert a link (prompts for target + description), =C-c C-o=
open the link under cursor, =C-c C-x C-v= toggle inline image display for
image links. Link targets can be URLs, other files, headings in the same file
(=*Heading text=), or roam node IDs (handled automatically by org-roam,
Lesson 7).

▶ Do this now: open =inbox.org=, =M-RET=, type =* Practice=, =TAB= to fold/unfold,
=M-RET= again for a sub-item, add a =- [ ] test= checkbox, =C-c C-c= to tick it.
Then add a second checkbox, put =[/]= in the parent heading, and watch the
counter update as you toggle each one.

* Lesson 2 — The visual layer: modern stars, live emphasis, focused writing (10 min)
None of this changes what your files *contain* — only how they're *displayed*.
Worth knowing so you're not confused when markup looks like it "disappeared."

*Org-modern* replaces the plain =*= =**= =***= stars with =◉ ○ ◈ ◇ ✦= in both
regular buffers and the agenda. It's pure display — the underlying file still
has plain asterisks, which is what you see if you open the file in any other
editor or with =cat=.

*Hidden emphasis markers:* =org-hide-emphasis-markers= is on, so =/italic/=
shows as /italic/ with the slashes hidden, not as literal slashes. *Org-appear*
is the fix for the annoying side effect of that: put your cursor *inside* a
bit of emphasized or linked text and the markers reappear live so you can edit
them, then hide again once you move off. Without org-appear you'd have to
guess where the invisible =*= =/= =_= boundaries are.

*Olivetti* centers and narrows the buffer to ~90 columns in Org buffers only —
pure readability, toggled automatically by the =org-mode-hook=, not something
you invoke by hand. If a buffer looks unusually narrow with wide margins,
that's this, not a bug.

*Theme integration:* =doom-themes-org-config= makes Org-specific faces (TODO
colors, priority colors, block delimiters) match whatever Doom theme is
active, rather than using Org's generic defaults.

▶ Do this now: open any note with a =/italic/= or =*bold*= word, move your
cursor onto it letter by letter and watch the =/= or =*= appear and disappear
as you enter and leave the word. That live reveal is org-appear; everything
else in this lesson is passive and needs no action.

* Lesson 3 — TODO states & workflows (the GTD core) (25 min)
A heading becomes a task when it starts with a TODO keyword. =C-c C-t= cycles
forward through the sequence; =S-right/S-left= on the keyword cycles either
direction without the menu.

*Your workflow, exactly as configured:* =BACKLOG(b) TODO(t) NEXT(n) DOING(o)
WAITING(w) REVIEW(r) | DONE(d) CANCELLED(c)=

The letter in parens is a *fast-select* key: with the cursor on a heading,
=C-c C-t= then that letter jumps straight to that state instead of cycling. The
=|= splits open states from terminal ones — everything after it counts as
complete for statistics and archiving.

What the states are for:

- =BACKLOG= — captured, not committed to. Deliberately absent from the
  dashboards, so a backlog item cannot nag you.
- =TODO= — committed, unscheduled.
- =NEXT= — the next physical action. A project with no NEXT is stalled, and the
  project dashboard says so in a column.
- =DOING= — in progress right now.
- =WAITING= — blocked on someone else. It blocks its subtasks, because a parent
  you cannot act on is not work you can do.
- =REVIEW= — finished, awaiting a second look.
- =DONE=, =CANCELLED= — terminal. Both write a =CLOSED:= timestamp into the
  =LOGBOOK= drawer.

Every knowledge file carries its own =#+TODO:= line mirroring this set. That is
not decoration: the kanban boards derive their columns from the TODO keywords
of the files they scan, so a file with a different set would change a board's
shape.

*Logging:* =org-log-done= is =time= and =org-log-into-drawer= is on, so marking
something DONE adds a collapsed =:LOGBOOK:= drawer rather than inline noise.

*Dependencies:* =org-enforce-todo-dependencies= is on. If a parent heading has
child headings that aren't DONE yet, Emacs will refuse to mark the parent DONE
and tell you why — a guardrail against marking a project complete while a
subtask is still open.

*Logging:* =org-log-done= records a timestamp into a drawer (not inline) every
time something is marked DONE, because =org-log-into-drawer= is on — so your
heading text stays clean and the history lives in a collapsed =:LOGBOOK:=
drawer under it.

▶ Do this now: in =work/tasks.org= add =* TODO Try the agenda=, =C-c C-t= to set
=NEXT=, then =C-c o a= → =a=. See it appear. Press =t= on it (in the agenda) to
mark DONE, then look under the heading for the =:LOGBOOK:= drawer that
appeared. Now make a heading with two TODO sub-children and try to mark the
parent DONE before finishing them — watch it refuse.

* Lesson 4 — The agenda system (25 min)
The agenda pulls every dated/TODO item from your agenda files (Lesson 0) into
one view. It's a *view*, not a file — editing in the agenda edits the real
heading in its real file.

| Key           | Action                          |
|---------------+----------------------------------|
| C-c o a       | open agenda dispatcher          |
| C-c o a → a   | day/week agenda                 |
| C-c o a → d   | your Dashboard (custom command) |
| (in agenda) t | cycle TODO                       |
| (in agenda) s / d | schedule / deadline          |
| (in agenda) f / b | next / prev day/week         |
| (in agenda) r | refresh (re-scan files)          |
| (in agenda) q | quit                             |

*Your dashboards* are three custom agenda commands defined in
=lisp/my-dashboards.el= — they are not built into Org:

| Key       | Dashboard | Contents                                        |
|-----------+-----------+-------------------------------------------------|
| =C-c k D= | Home      | today's schedule, next actions, doing, waiting, review |
| =C-c k P= | Projects  | open project tasks grouped by state             |
| =C-c k L= | Learning  | open learning tasks, revision, next actions     |

The home view is grouped with =org-super-agenda= into Overdue / Today / Soon.
The project and learning views are restricted to their own directories, so a
learning task never appears on the project page. Super-agenda grouping applies
to these views only; a plain =C-c o a= agenda is untransformed.

Static versions of the same information live in the dashboard files
(=~/knowledge/dashboards/=), as blocks generated from org-ql queries. Refresh
them with =C-c k b=. They exist because a terminal makes the agenda buffer hard
to skim, and because a file can be grepped.

▶ Do this now: =C-c k D= and read the home dashboard top to bottom. Then
=C-c k P= and =C-c k L= to see the same data cut by area. Then =C-c o a= → =a=
for the plain day/week view and compare — same underlying data, different
shape. Press =q=, confirm you're back exactly where you started.

* Lesson 5 — Capture → Refile (don't break flow) (25 min)
*Capture* = drop a thought in 5 seconds without leaving what you're doing.
*Refile* = move it to its real home later. These exist as two separate steps
on purpose: deciding *what* to write and deciding *where it belongs* are
different kinds of thinking, and mixing them is what makes people avoid
capturing things at all.

Your capture keys (each opens a template, write, then =C-c C-c= to file it):
| Key     | Captures to                     |
|---------+---------------------------------|
| C-c n i | inbox                           |
| C-c n j | journal entry (today, datetree) |
| C-c n v | review item (SRS)               |
| C-c n r | reading note                    |
| C-c n w | work task                       |
| C-c n W | work project                    |
| C-c n t | personal task                   |
| C-c n p | personal project                |

One more =C-c n= binding that isn't a capture template: =C-c n s= runs
=my/learn-search=, a full-text ripgrep search across every file in
=~/knowledge/= — the fastest way to find "where did I write about X"
when you don't remember which file or node it's in.

*Anatomy of a template:* each one is a target file + a heading pattern +
sometimes properties. The journal template (=C-c n j=) uses a *datetree* —
instead of one flat list, it auto-creates a Year → Month → Day heading
structure the first time you capture on a given day, then files under today's
date every time after. The review template (=C-c n v=) adds a hidden
=REVIEW_COUNT= property at 0 — that counter is what Lesson 9's interval logic
reads and increments.

*Refile mechanics:* =C-c C-w= on any heading opens a completion prompt built
from =org-refile-targets= — every heading in every agenda file, up to 3 levels
deep (=maxlevel 3=). Two settings make this pleasant instead of tedious:
=org-refile-use-outline-path='file= shows each candidate as a breadcrumb
prefixed by the *file name only* (directory stripped), e.g.
=projects.org/Q3 Migration/Backend=, so you're not guessing which
"Backend" you're picking among several within the same file. (Two files with
the same basename in different directories, like =work/projects.org= and
=personal/projects.org=, would show identical prefixes — worth knowing if you
ever rename files that way.) =org-refile-use-cache=t= means that
breadcrumb list is built once and cached rather than rescanned on every
refile, so it stays fast even with hundreds of headings. If you add a new
heading and it doesn't show up in the refile list yet, =C-0 C-c C-w= (zero as
the prefix arg) forces a cache refresh.

=org-refile-allow-creating-parent-nodes='confirm= means you can type a
brand-new heading name at the refile prompt (not just pick an existing one)
and it will ask before creating it — useful for "file this under a project
that doesn't have a section yet" without leaving the refile prompt to go
create one first.

▶ Do this now: =C-c n i=, type =Buy a notebook=, =C-c C-c=. Open =inbox.org=,
put cursor on it, =C-c C-w=, refile it into an existing heading in
=personal/tasks.org= (note the breadcrumb path shown). Then try =C-c n j= and see the
datetree get created under today's date in =journal.org=.

Habit to build: capture all day into inbox → once a day, refile the inbox to
zero.

* Lesson 6 — Scheduling, deadlines, habits, archiving (20 min)
| Key     | Action                                  |
|---------+-------------------------------------------|
| C-c C-s | SCHEDULED — "start working on date"     |
| C-c C-d | DEADLINE — "must be done by date"       |
| C-c o A | archive this subtree (out of agenda)    |

*Scheduled vs Deadline:* scheduled = when it appears on your plate; deadline =
the hard date the agenda warns you about in advance, counting down.

*Repeater syntax* (typed after the date, e.g. =<2026-07-10 +1w>=):
- =+1w= — shift forward by exactly 1 week from the *original* date, every time, regardless of when you actually did it (good for "every Monday" style recurrence).
- =++1w= — like =+1w= but skips forward past any dates you missed, landing on the next one still in the future (good for "weekly, but don't pile up missed ones").
- =.+1w= — 1 week from *today* (the day you mark it done), not from the original date — this is what habits use, since a habit's next occurrence should count from when you actually did it.

*Habits:* give a repeating task =:PROPERTIES: :STYLE: habit :END:= and a
=SCHEDULED= with a =.+= repeater. The agenda draws a consistency graph next to
it. Two settings shape that graph: =org-habit-graph-column=55= fixes which
column the graph starts at (so it lines up regardless of heading text length),
and =org-habit-show-habits-only-for-today=t= means the graph only appears on
today's agenda line, not stacked across every future day — keeps the agenda
readable.

*Archiving (hygiene):* DONE/MASTERED/DROPPED items pile up and slow the agenda
and refile-cache down. =C-c o A= moves a finished subtree out, governed by
=org-archive-location = "%s_archive::* Archived"= — the =%s= is replaced with
the current file's name, so archiving a heading in =work/tasks.org= creates or
appends to =work/tasks.org_archive=, under a top-level =* Archived= heading in
that archive file. Archived items are off the agenda (archive files aren't
agenda files) but still on disk and still =grep=-able. Do this weekly.

▶ Do this now: schedule a task for tomorrow (=C-c C-s=, type =+1=), mark another
DONE and =C-c o A= to archive it. Open the =_archive= file that got created and
confirm the =* Archived= heading and your item are there. Then set up one real
habit with a =.+1d= repeater and =:STYLE: habit:=, and check the agenda for
its consistency graph the next morning.

* Lesson 7 — Org-Roam: your knowledge graph (35 min)
Every note is a *node*. Nodes link to each other; *backlinks* show what points
at the current note. This is your "second brain" — the part of this setup
that behaves least like a task manager and most like a wiki you write to
yourself.

| Key     | Action                         |
|---------+----------------------------------|
| C-c o r | find or create a node          |
| C-c o i | insert a link to another node  |
| C-c o s | search all nodes (ripgrep-backed)|
| C-c o u | open the visual graph (browser)|
| C-c n k | new *concept* node (template)   |
| C-c n q | new *question* node (template)  |

*How org-roam actually finds things:* every node lives as a plain heading or
file in =~/knowledge/= (same directory as everything else — roam notes
aren't segregated). A SQLite database (=org-roam-db-autosync-mode=) indexes
titles, tags, and links so =C-c o r= can search instantly instead of
re-scanning every file on every keystroke. If the graph ever looks stale after
manually editing a file outside Emacs, =M-x org-roam-db-sync= forces a
rebuild — this is a cache, not the source of truth, so it's always safe to
rebuild.

*Completion everywhere:* =org-roam-completion-everywhere=t= means you can type
=[[= almost anywhere in an Org buffer, even outside a dedicated roam workflow,
and get node-completion — you don't have to remember =C-c o i= specifically if
=[[= is faster muscle memory for you.

*Templates:* =C-c n k= (concept) scaffolds What / Why / When / Code / Links
sections — use it for "I learned a concept and want to actually retain it."
=C-c n q= (question) is a lighter template for an open question you want to
revisit, without the full concept scaffold. Both are org-roam capture
templates, distinct from the =C-c n= task-capture templates in Lesson 5 —
same prefix key, different subsystem, worth keeping straight.

*Backlinks:* =M-x org-roam-buffer-toggle= opens a side panel showing every
node that links *to* the one you're currently in. This is the payoff of
linking consistently — a note becomes more valuable over time as more things
point at it, and the backlink panel is how you discover those connections
without remembering they exist.

*The visual graph* (=C-c o u=, via org-roam-ui) opens a browser view of your
whole node network. =org-roam-ui= is configured with =sync-theme=t= (matches
your Emacs theme), =follow=t= (the graph highlights whatever node you're
currently visiting in Emacs), and =update-on-save=t= (edits reflect live) —
but =open-on-start=nil=, so it never launches automatically at Emacs startup,
only when you press =C-c o u=.

▶ Do this now: =C-c n k=, title "Python decorators", fill =What/Why/When=. Then
=C-c n k= again "Higher-order functions". In the first note, =C-c o i= and link
to the second. Open =C-c o u= to see them connected in the graph, then =M-x
org-roam-buffer-toggle= inside the second note and confirm the first shows up
as a backlink.

* Lesson 8 — People tracking (20 min)
Person nodes are roam notes tagged =:person:=, filed into the =people/=
subdirectory automatically by the capture template, with structured
interaction logs.

| Key     | Action                                |
|---------+-----------------------------------------|
| C-c n P | create a person node                  |
| C-c n x | log an interaction with a person      |
| C-c o r | find a person by name (same as any node)|

*Why person nodes are roam nodes and not tasks:* a person isn't a thing you
complete — it's an entity you accumulate context on over time, which is
exactly what roam nodes with backlinks are good at. Every project note that
mentions someone can link to their person node, and their person node's
backlink panel becomes a running "everything connected to this person" view.

*=my/roam-log-interaction=* (bound to =C-c n x=) is a small custom function,
not a stock org-roam feature: it prompts you to pick an existing person node,
then appends a timestamped entry under a =* Interactions= heading in their
file automatically — you never have to navigate to their file, find the
right heading, and format the timestamp by hand.

▶ Do this now: =C-c n P=, name someone, fill =* Who= and =* Find Them=. Confirm
the node landed next to its siblings. Nodes are files, not a database;
type what you talked about — it timestamps under =* Interactions=
automatically. Add a =* Follow-up= checkbox and tick it with =C-c C-c= when
done.

* Lesson 9 — Spaced repetition (remember what you learn) (20 min)
Your homemade SRS: items get =REVIEW= state + a scheduled date. You review on
the due date and reschedule at growing intervals — the classic spaced-repetition
idea, implemented in Elisp against your own =REVIEW_COUNT= property instead of
a dedicated flashcard app.

Intervals, from =my/learn-reviewed=: =1 → 3 → 7 → 14 → 30 → 60 days=, then
=MASTERED= after the 6th successful review.

| Key     | Action                                   |
|---------+---------------------------------------------|
| C-c n v | capture a review item (sets REVIEW_COUNT=0) |
| C-c n a | open the review agenda (today's due items)  |
| C-c n d | mark reviewed → advance state and reschedule|

*What =C-c n d= actually does:* it reads the item's current =REVIEW_COUNT=,
looks up the next interval in the =1/3/7/14/30/60= table, sets a new
=SCHEDULED= date that many days out, and increments the counter — all in one
keystroke. On the 6th successful review it still applies the final +60d
reschedule, but *also* flips the TODO state to =MASTERED= in that same step —
that state change is why MASTERED items stop appearing in =C-c n a= afterward,
not the reschedule being skipped.

*Why this beats a plain TODO for review items:* a normal reschedule is manual
and you'd have to remember the interval yourself. This automates the interval
math so the *only* decision you make on review day is "did I recall it or
not" — everything else (next date, counter, eventual graduation) is handled.

▶ Do this now: =C-c n v=, "What does org-refile do?", =C-c C-c=. Edit its
SCHEDULED date to today (or wait for tomorrow): =C-c n a= to see it, recall the
answer, =C-c n d= to push it to the next interval. Check the =REVIEW_COUNT=
property (it'll be in the properties drawer) to see it increment.

* Lesson 11 — Time tracking: clock + pomodoro (20 min)
*Clock* logs real time against a heading. *Pomodoro* runs focused 25-min
blocks and clocks automatically while it runs.

| Key     | Action                            |
|---------+---------------------------------------|
| C-c o I | clock in (start timer on heading) |
| C-c o O | clock out                         |
| C-c o R | insert a clock report table       |
| C-c o e | set an effort estimate            |

*Persistence:* =org-clock-persist=t= (with =org-clock-persistence-insinuate=)
means if Emacs crashes or you quit while clocked in, the running clock resumes
on restart instead of silently losing the time — clock state survives the
session, not just the buffer.

*Mode line:* =org-clock-mode-line-total='today= shows *today's* accumulated
time for the current clock in the mode line, not the all-time total for that
heading — useful for "how much have I actually worked on this today" at a
glance without opening a report.

*Effort vs actual:* =C-c o e= sets an *estimate* before you start (e.g. "2h").
It's informational only — nothing enforces it — but a clock report (=C-c o R=)
next to an effort estimate is how you calibrate your own estimates over time.

*Pomodoro:* cursor on a task heading → =M-x org-pomodoro= → a 25-minute timer
(=org-pomodoro-length=25=), automatic break, and the time gets logged to the
heading exactly like a manual clock-in would — pomodoro is a thin automated
wrapper around clocking, not a separate time-tracking system.

▶ Do this now: on any task, =C-c o I=, do something for a minute, =C-c o O=.
Then =C-c o R= to see a time report table appear. Set an effort estimate with
=C-c o e= on a different task, then run one =M-x org-pomodoro= session against
it and compare the logged time to your estimate.

* Lesson 12 — Tables (15 min)
Org has a full spreadsheet in plain text.

Type a line starting with =|=, press =TAB= — it becomes a table and keeps
aligning as you go. =C-c -= inserts a header separator line.

| Key          | Action                    |
|--------------+----------------------------|
| TAB          | next cell (new row at end)|
| C-c C-c      | realign                   |
| C-c ^        | sort column               |
| M-LEFT/RIGHT | move column               |
| M-UP/DOWN    | move row                  |

Formulas: a column can compute. =:= field formula, =C-c == to enter one, e.g.
=$3=$1*$2= then =C-c C-c= to recalculate. Formulas can reference whole columns
(=@2$3..@>$3= = "column 3, row 2 to the last row") for things like a running
total — useful for effort/clock-report tables you build by hand alongside the

* Lesson 16 — How the config fits together (10 min, read-only)
No new keys here — this is the map so the previous 16 lessons stop feeling
like 16 unrelated tools.

Everything in this tutorial comes from *one* section of =init.el= (the Org
section, roughly the middle third of the file). The layering, bottom to top:
1. *Org core* — headings, TODO keywords, agenda-files, capture templates,
   refile targets. Everything else depends on this layer existing.
2. *Visual layer* — org-modern, org-appear, olivetti, doom-themes-org-config.
   Purely cosmetic; could be deleted with zero effect on your data.
3. *Query/view layer* — org-super-agenda, org-ql, org-kanban, the Dashboard
   custom command. These all *read* core Org data and reshape how it's shown;
   none of them store anything of their own.
4. *Org-roam and its satellites* — org-roam itself, consult-org-roam (fuzzy
   search), org-roam-ui (visual graph). Roam's SQLite database is a rebuildable
   cache over the same plain files as everything else, per Lesson 7.
5. *Custom Elisp glue* — the =my/roam-capture-concept=, =my/roam-log-interaction=,
   =my/learn-review=, =my/learn-reviewed=, =my/learn-search= functions bound
   under =C-c n=. These are the only parts of this whole system that are
   bespoke code rather than
   package configuration — if something in the SRS or people-tracking flow
   ever behaves unexpectedly, this is where to look first, not in a package's

Practical upshot: layers 2–4 are all optional relative to layer 1. If org-roam
or org-ql ever broke or got removed, your plain TODO/agenda/capture/refile
workflow (Lessons 3–6) would be completely unaffected, because nothing in
that core layer depends on the layers built on top of it.

* Lesson 17 — Search & Navigation (Consult, Avy, Expand-region) (20 min)
These three packages handle "getting somewhere fast" — inside a buffer, across
buffers, and across the whole project. Learning them removes almost all manual
=C-f= / =C-b= navigation from your muscle memory.

** Consult — search everywhere
=consult= is a collection of enhanced built-in commands that feed results into
the =vertico= minibuffer with live preview.

| Key                 | Action                                              |
|---------------------+-----------------------------------------------------|
| C-s                 | standard incremental search (=isearch-forward=)    |
| M-s l (or C-c s s)  | =consult-line= — live-search lines in current buffer |
| M-s r (or C-c s r)  | =consult-ripgrep= — grep across the whole project    |
| M-s i (or C-c s i)  | =consult-imenu= — jump to any function/heading       |
| M-s t (or C-c s t)  | =consult-todo= — list all TODO/FIXME/HACK comments   |
| C-c f r             | =consult-recent-file= — pick from recently opened files |
| C-x b               | =consult-buffer= — switch buffer (remapped with live preview; also C-c b b) |
| M-.                 | preview result under cursor (=consult-preview-key=) |
| <                   | narrow results to a category (=consult-narrow-key=) |

*How preview works:* as you move through candidates in the minibuffer, =M.=
temporarily visits that file/line so you can read context without committing.
Press =RET= to confirm, =C-g= to abort and return exactly where you started.

*=consult-ripgrep= vs =project-find-regexp=:* ripgrep is faster and respects
=.gitignore=; use =C-c s r= for code search and save =project-find-regexp= for
when you need Emacs regex syntax specifically.

*=xref= integration:* =consult-xref= is set as the display function for both
=xref-find-references= and =xref-find-definitions=, so LSP cross-references
(=C-c c d=, covered in Lesson 20) also open in the consult minibuffer.

** Avy — jump to any visible character
=avy= is faster than =isearch= when the target is visible on screen.

| Key   | Action                                                       |
|-------+--------------------------------------------------------------|
| C-c j | =avy-goto-char-2= — type two chars, jump instantly anywhere  |

Type two characters → avy overlays single-letter hints on every match currently
on screen → press the hint letter → cursor jumps there. Zero intermediate steps.
Works across windows. When the target is on screen, this is consistently faster
than any other navigation method.

** Expand-region — grow selection semantically
| Key | Action                                          |
|-----+-------------------------------------------------|
| C-= | =er/expand-region= — expand selection by one unit |

Each press expands the selection outward by one syntactic unit: word → symbol →
string → expression → function body → file. Works across all major modes.
Especially useful for "select this whole argument" or "select this block" without
counting characters. Press =C-= repeatedly; the selection only grows, never
shrinks (use =C-g= to abort the whole selection).

▶ Do this now: open any code file. =C-s= and type part of a function name —

* Lesson 18 — Completion in depth (Vertico, Orderless, Corfu, Embark) (20 min)
Your config has two distinct completion systems that don't interfere: *Vertico*
for the minibuffer (file paths, commands, headings) and *Corfu* for in-buffer
code completion. Understanding each prevents the confusion of "why isn't
Tab doing what I expect here."

** Vertico + Orderless — minibuffer
Vertico replaces the default completion list with a vertical, scrollable
candidate list that responds to =orderless= filtering.

| Key            | Action                            |
|----------------+------------------------------------|
| any minibuffer | type space-separated fragments     |
| TAB / RET      | select candidate                   |
| C-n / C-p      | move through candidates            |
| DEL            | delete path component (in files)   |
| C-x C-d        | =consult-dir= — jump to a directory |
| C-x C-j        | (in vertico) jump into a file there |

*Orderless matching:* type =org cap= to match "org-capture", =cap org= works
too — fragment order doesn't matter. Separate fragments with spaces. This is
why you never need to type exact prefixes in the minibuffer anymore.

*Marginalia:* annotations appear to the right of each candidate automatically
(docstrings for commands, file sizes for files, etc.) — that's =marginalia=,
always on, no key needed.

** Corfu — in-buffer code completion
Corfu shows a popup of completions while you type in code buffers. It's
triggered automatically after 2 characters with a 0.15s delay.

| Key         | Action (inside the popup)          |
|-------------+------------------------------------|
| C-n / C-p   | move through candidates            |
| TAB / RET   | insert selected candidate          |
| C-g / ESC   | dismiss popup                      |
| (auto)      | popup appears 0.15s after typing   |

*RET is unbound in corfu-map:* deliberately. RET always inserts a newline, never
confirms a completion — so you can press RET in the middle of typing without
accidentally completing. Use TAB to complete explicitly.

*Corfu-popupinfo:* after 0.5s hovering on a candidate, a secondary popup shows
its full documentation. This pulls from LSP (when eglot is active) or from
Elisp docstrings.

*Cape* extends what corfu can complete: =cape-file= (file paths anywhere),
=cape-keyword= (language keywords in prog buffers), =cape-dabbrev= (words from
open buffers), =cape-elisp-symbol= (in Emacs Lisp). These are added to the
completion pipeline silently — you don't invoke them directly.

** Embark — act on any candidate
Embark adds a "right-click menu" to any candidate in vertico or at point.

| Key   | Action                                            |
|-------+---------------------------------------------------|
| C-.   | =embark-act= — open action menu on thing at point  |
| C-c . | =embark-dwim= — do the default action for thing at point |

Examples of what the action menu offers, depending on context:
- On a *file candidate* in vertico: delete, rename, copy path, open in dired
- On a *function name* at point: describe, find definition, xref
- On a *URL* at point: browse, copy, org-store-link
- On a *consult-ripgrep result*: open in =wgrep= to edit all matches at once

*wgrep workflow:* =C-c s r= to ripgrep → =C-. → w= to enter wgrep mode →
edit any match inline → =C-c C-c= to apply all edits to the real files. This
is how you do a project-wide rename without a dedicated refactoring tool.

▶ Do this now: =M-x= and start typing — notice orderless fragments working.
Open a Python file, type a function name prefix, wait for corfu popup, navigate
it with =C-n/C-p=, dismiss with =C-g=. Then =C-c s r= for a word, =C-.= on a
result, press =o= to open it in another window.

* Lesson 19 — Editor ergonomics (Symbol-overlay, vundo, helpful, which-key) (15 min)
These four packages remove specific friction points: finding all occurrences of
a symbol, navigating undo history, getting real documentation, and discovering
keys without memorizing them.

** Symbol-overlay — highlight and navigate occurrences
| Key   | Action (in prog buffers)                           |
|-------+----------------------------------------------------|
| M-i   | highlight / unhighlight all occurrences of symbol at point |
| M-n   | jump to next occurrence                             |
| M-p   | jump to previous occurrence                         |
| M-Q   | query-replace this symbol across the buffer         |
| q     | (on a highlighted symbol) remove all highlights     |

=symbol-overlay-mode= is on in all =prog-mode= buffers. Move the cursor onto
any identifier and press =M-i= to highlight every occurrence. The highlights
persist across the file so you can read occurrences far from where you started.
=M-Q= is a scoped =query-replace= — it only touches that exact symbol, not
partial matches inside longer words.

*Difference from =C-c c r= (eglot-rename):* symbol-overlay is buffer-only and
purely textual; eglot-rename asks the language server for every reference across
the whole project and renames them semantically. Use symbol-overlay for quick
local navigation; use eglot-rename for a real refactor.

** vundo — visual undo tree
| Key   | Action                            |
|-------+-----------------------------------|
| C-x u | open the visual undo tree (vundo) |

Standard =C-z= undo is a linear sequence; once you undo and type something new,
the "redone" history is lost. Vundo makes the history a *tree*: every undo
branch is preserved and navigable. In the vundo buffer, =f/b= move forward/back
through history, =l/h= move between branches. =q= closes it and leaves the
buffer in whatever state you landed on. Especially useful after "I undid too
much and now I can't find my edit."

** Helpful — better help buffers
| Key       | Action                                    |
|-----------+-------------------------------------------|
| C-h f     | describe a function (with source + examples) |
| C-h v     | describe a variable (with current value)  |
| C-h k     | describe a key binding                    |
| C-h .     | describe whatever is at point             |
| C-h x     | describe an interactive command           |

=helpful= replaces standard =describe-function=, =describe-variable=, and =describe-key=
with richer buffers that show the actual source code, cross-links, and usage
examples. =C-h .= is the most useful: point at any symbol in your =init.el=
or any other buffer and get instant, rich documentation without leaving context.

** Which-key — discover keys interactively
| Key (example) | Action                                    |
|---------------+-------------------------------------------|
| C-c (pause)   | shows all bindings under C-c              |
| C-c g (pause) | shows all bindings under C-c g            |

=which-key= is always on with a 0.3s delay. Press any prefix key and pause —
a popup lists every continuation available. This is how you explore unfamiliar
keymaps without reading documentation. Combined with the cheatsheet, it means
you almost never need to guess or look up a key cold.

▶ Do this now: open a code file, put cursor on a variable name, =M-i= to
highlight it, =M-n/M-p= to navigate occurrences. Then =C-x u= and in the vundo
buffer make a few edits, undo with =f/b=, switch branches with =l/h=, and =q=
to commit. Finally =C-c h .= on any function name and read the helpful buffer
that opens.

* Lesson 20 — Git with Magit + diff-hl (25 min)
Magit is a full git porcelain inside Emacs. After a week with it, the command
line feels slow by comparison — the staging/diff/commit/log workflow is faster
because it's keyboard-driven with tab-expand-to-show-diff at every level.

| Key       | Action                                        |
|-----------+-----------------------------------------------|
| C-c g g   | =magit-status= — the main Magit window         |
| C-c g c   | commit                                        |
| C-c g p   | push                                          |
| C-c g u   | pull                                          |
| C-c g f   | fetch                                         |
| C-c g l   | log (current branch)                          |
| C-c g d   | diff dwim (staged, unstaged, or HEAD diff)    |
| C-c g b   | branch operations                             |
| C-c g a   | blame (annotate every line with commit)       |
| C-c g s   | stash                                         |
| C-c g n   | jump to next hunk (diff-hl)                   |
| C-c g N   | jump to previous hunk (diff-hl)               |

*The Magit status buffer:* =C-c g g= opens the hub of everything. Sections show
unstaged changes, staged changes, untracked files, recent commits. Inside that
buffer:
- =TAB= on any file or hunk → expand to show the diff
- =s= on a hunk or file → stage it
- =u= → unstage
- =c c= → commit (opens commit message buffer; =C-c C-c= to finish)
- =P p= → push
- =F p= → pull
- =q= → close

*Staging hunks, not files:* the most powerful Magit habit. Expand a file with

(green), modified (yellow), or deleted (red) relative to HEAD, updated live as
you type. =C-c g n/N= jumps between those fringe markers. =diff-hl-flydiff-mode=
is on — the fringe updates after each buffer modification, not just on save.

*magit-blame (=C-c g a=):* annotates every line with author + date + commit
summary. Press =q= in the blame buffer to exit back to normal. Extremely useful
for "who changed this line and why."

* Lesson 21 — LSP with Eglot (built-in) (20 min)
Eglot connects Emacs to a language server (LSP) for the language you're
editing. The server provides type-aware completion, real-time errors, go-to-
definition, references, rename, and code actions — all through a standard
protocol, so the same Emacs UI works for Python, C++, TypeScript, etc.

| Key       | Action                                              |
|-----------+-----------------------------------------------------|
| C-c c r   | rename symbol (project-wide, via LSP)               |
| C-c c a   | code actions (fix import, extract variable, etc.)   |
| C-c c i   | find implementations of a symbol                    |
| C-c c d   | find all references (=xref-find-references=)        |
| M-.       | go to definition (built-in xref, enhanced by eglot) |
| M-,       | go back (xref pop stack)                            |
| C-c e n   | jump to next Flymake error                          |
| C-c e p   | jump to previous Flymake error                      |
| C-c e l   | list all errors with consult (=consult-flymake=)    |

*Eglot activates automatically* for Python, C, and C++ files via hooks in your
config — you never run =M-x eglot= by hand. When it connects, the mode line
shows the server name. It disconnects automatically when the last managed buffer
is closed (=eglot-autoshutdown=t=).

*Which server is used:* eglot picks the first available server for each
language. For Python: =pyright= or =pylsp= (whichever is on PATH). For C/C++:
=clangd=. Install them through your package manager or conda environment.

*Inlay hints* (=eglot-inlay-hints-mode=) are on automatically in managed
buffers — grey annotations appear inline showing inferred types, parameter
names for positional arguments, etc. They're display-only; the file is
unchanged.

*Flymake* (section 9 in =init.el=) is the built-in error-display system that
eglot feeds into. Errors and warnings appear as colored underlines; the right
fringe shows indicators. =C-c e l= lists all of them via =consult-flymake= so
you can jump to each one. =flymake-byte-compile= is intentionally disabled for
=emacs-lisp-mode= (would be too noisy when editing =init.el=).

*eglot-code-actions (=C-c c a=):* the most underused feature. Put cursor on
an error, =C-c c a= — the server offers context-specific fixes ("add missing
import", "add type annotation", "implement abstract method"). In Python with
pyright this often resolves import errors in one keystroke.

▶ Do this now: open a Python file in a conda environment (=C-c v a= to
activate one — see Lesson 23). Eglot should connect automatically. Type an

Dape is a Debug Adapter Protocol (DAP) client — the same protocol VS Code uses.
It works with any language that has a debug adapter installed (Python =debugpy=,
C/C++ via =codelldb= or =lldb-vscode=, etc.).

| Key       | Action                                       |
|-----------+----------------------------------------------|
| C-c c b   | toggle breakpoint on current line            |
| C-c c B   | start a debug session (=dape=)               |

Inside a Dape session (additional keys available in the dape buffer):
| Key   | Action                      |
|-------+-----------------------------|
| n     | next (step over)            |
| i     | step into                   |
| o     | step out                    |
| c     | continue                    |

*Starting a session (=C-c c B=):* Dape prompts for a configuration. For Python

*Breakpoints:* =C-c c b= toggles a red dot in the fringe on the current line.

*Python setup:* =pip install debugpy= in your conda env, then =C-c c B= →

* Lesson 23 — Formatters, runners & Conda (15 min)
** Apheleia — automatic formatting on save
=apheleia-global-mode= is on. Every time you save a file, the appropriate
formatter runs in the background and patches the buffer with only the changed
lines (so the cursor doesn't jump).

| Language          | Formatter used  |
|-------------------+-----------------|

| Markdown          | =prettier=      |

Install the formatters through your system package manager or =pip=. If a

=C-c c f= forces an immediate format without saving (=apheleia-format-buffer=).

Both use the built-in =compile= command and open a =*compilation*= buffer where

The C++ runner compiles to =<filename>.out= in the same directory, then runs it

| C-c w K   | shrink window vertically                     |
| C-c w J   | enlarge window vertically                    |
| C-c w =   | balance all windows equally                  |
| C-c w f   | toggle fullscreen                            |
| C-c w u   | undo window layout (winner-undo)             |
| C-c w U   | redo window layout (winner-redo)             |
| M-o       | =other-window= (cycle through windows)       |

*Winner mode:* every time the window layout changes (split, close, resize),
winner records it. =C-c w u= steps back through layouts — invaluable after
something (magit, dape, org-agenda) opens extra windows and you want your
previous layout back in one keystroke.

** Tab-bar — workspace tabs
Tab-bar is active with =tab-bar-show=1= (shows the tab bar only when more than
one tab exists). Tabs are independent window layouts, not just buffers.

| Key       | Action                              |
|-----------+-------------------------------------|
| C-x t 2   | new tab                             |
| C-x t 0   | close current tab                   |
| C-x t n   | next tab                            |
| C-x t p   | previous tab                        |
| C-x t r   | rename current tab                  |
| C-x t t   | switch to tab by name               |

Typical usage: one tab for "code", one for "org/notes", one for "magit". Each
tab remembers its own window splits independently. New tabs always open
=*scratch*= (=tab-bar-new-tab-choice="*scratch*"=).

** The mode line (doom-modeline)
Your mode line (the bar at the bottom of each window) shows, left to right:
- Buffer state: =%= modified, =-= read-only
- Branch name and diff summary (from diff-hl)
- Buffer name + major mode icon (nerd-icons)
- Current function name (which-function-mode)
- LSP server name (when eglot is connected)
- Flymake error/warning counts
- Position and line number
- Clock (when org-clock is running)

=doom-modeline-icon=t= shows icons when in a GUI frame; in terminal mode the
icons are suppressed automatically (checked per-frame via =after-make-frame-functions=).

▶ Do this now: split your frame (=C-x 3=), move between windows with =C-c w h/l=,
resize with =C-c w L=, then =C-c w u= to get back to one window. Create two tabs
with =C-x t 2=, rename one with =C-x t r=, switch between them with =C-x t n/p=.

* Lesson 25 — AI assistant (gptel + LM Studio) (15 min)
=gptel= connects to a locally running LM Studio instance serving the model
=gemma-4-e4b= on =localhost:1234=. All inference is local — no cloud API key,
no data leaving your machine.

| Key       | Action                                          |
|-----------+-------------------------------------------------|
| C-c a c   | open a new gptel chat buffer                    |
| C-c a s   | send region or buffer to the model              |
| C-c a r   | rewrite selected region (AI rewrite in place)   |
| C-c a m   | =gptel-menu= — configure model/params           |

*How the chat buffer works:* =C-c a c= opens a =*gptel*= buffer in org-mode
(=gptel-default-mode='org-mode=). Type your prompt under a heading, =C-c a s=
sends it, the response streams in below. The conversation accumulates in that
buffer — every send includes the full context above it, so you can have a
multi-turn conversation.

*Rewrite (=C-c a r=):* select a region of prose or code, =C-c a r=, type an
instruction ("make this more concise", "convert to list comprehension"), and the
selected region is replaced with the model's output. Works in any buffer.

*Send (=C-c a s=):* without a selection, sends the whole buffer as context.
With a selection, sends only that region. Useful for "explain this function" —
select the function, =C-c a s=.

*gptel-menu (=C-c a m=):* a transient popup to change the model (if you have
multiple loaded in LM Studio), adjust temperature, toggle streaming, etc.

*LM Studio prerequisite:* LM Studio must be running with a model loaded and the
local server enabled on port 1234. Start it from LM Studio's app before using
any =C-c a= keys.

▶ Do this now: make sure LM Studio is running with a model loaded. =C-c a c=
to open the chat buffer. Type a question under the default heading, =C-c a s=
to send, watch the response stream in. Then select a paragraph of text anywhere,
=C-c a r= → "make this more concise" → RET.

* Lesson 26 — Markdown (5 min)
=markdown-mode= activates automatically for =.md= and =.markdown= files.

| Key         | Action                                        |
|-------------+-----------------------------------------------|
| C-c C-e     | export / preview (via pandoc)                 |
| C-c C-o     | open link at point                            |
| C-c C-l     | insert a link                                 |
| TAB         | fold/unfold section (like Org headings)       |
| C-c C-n/p   | next/previous heading                         |

*Configuration highlights:*
- =markdown-command= is =pandoc= — export and preview require pandoc installed
- =markdown-fontify-code-blocks-natively=t= — fenced code blocks (=```python=)
  are syntax-highlighted with their real language's font-lock rules
- =markdown-header-scaling=t= — heading levels have proportional text sizes
- =markdown-hide-urls=t= — long URL text is hidden; =C-c C-o= still opens them
- =olivetti-mode= and =visual-line-mode= are on automatically (same as org-mode)
  so Markdown files get the same centered, soft-wrapped writing experience

*Pandoc:* install with =brew install pandoc=. Without it, =C-c C-e= fails
silently; all other features still work.

▶ Do this now: open or create a =README.md=. Notice the code block highlighting
and Olivetti centering. =C-c C-l= to insert a link to a URL. If pandoc is
installed, =C-c C-e= to preview.
